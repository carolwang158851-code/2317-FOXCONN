# EPISTEMIC_BUFFER.md
# 認識論不確定性緩衝層（Epistemic Uncertainty Buffer）
# 版本：v1.0.0 | 建立日期：2026-06-26 | 狀態：ACTIVE
# 適用：MIDR v2.4+ 所有閾值決策

---

## 一、設計目的

將「後見之明偏誤」從隱性系統風險轉為顯性管理對象。

**核心原則**：
- 不試圖消除認識論不確定性（這在邏輯上不可能）
- 讓每個閾值決策附帶其可靠性的誠實評估
- 當可靠性低於臨界值時，自動觸發保護機制

**不適用範圍**：
- P1規則（現金守門員）：基於確定性約束，不依賴市場預測，免除緩衝層
- 配息收入計算：確定性數字，不需要緩衝層

## 二、失效案例定義

### 2.1 什麼是「失效案例」

```
失效案例 = 閾值決策在事後被證明方向錯誤的案例

判斷標準（365天後回顧）：
  若閾值觸發 ADD/HOLD_ADD 類訊號：
    → 365天後股價 < 觸發時股價 × 0.90（虧損超過10%）= 失效
    → 365天後股價 ≥ 觸發時股價 × 0.90 = 有效

  若閾值觸發 BLOCK/STRONG_BLOCK 類訊號：
    → 365天後股價 > 觸發時股價 × 1.20（漲幅超過20%）= 失效（過度保守）
    → 365天後股價 ≤ 觸發時股價 × 1.20 = 有效

注意：失效不等於「規則錯誤」，只代表「在此案例中結果不如預期」
```

### 2.2 失效案例的時間權重

```
時間衰減公式：
  weight(t) = exp(-λ × age_in_quarters)

  其中：
    age_in_quarters = 案例距今的季度數
    λ = 0.15（衰減係數，每季衰減約14%）

  效果：
    當季案例：weight = 1.00（100%）
    1年前案例：weight = 0.55（55%）
    2年前案例：weight = 0.30（30%）
    3年前案例：weight = 0.17（17%）
    5年前案例：weight = 0.05（5%，幾乎忽略）

設計理由：
  市場結構性轉變（如AI題材爆發）使舊案例的參考價值快速衰減
  λ=0.15 對應「2年前的案例只有當前的30%參考價值」
  這是一個保守設定，避免過度依賴近期數據

特殊情況：
  若案例發生在已知的結構性轉變之前（如2024Q1 AI爆發前）
  可手動標記 structural_break=true，weight 額外乘以 0.5
```

## 三、觸發審查的樣本數門檻

### 3.1 最低樣本數要求

```
觸發「閾值重新審查」需要同時滿足：

條件A：同類情境的總案例數 ≥ 5
  理由：少於5個案例，任何統計結論都不可靠
  當前狀態：ADD+CAUTION=6（✅），BLOCK+CAUTION=3（❌不足）

條件B：失效案例數 ≥ 2
  理由：單一失效可能是偶然，2個以上才有模式意義
  
條件C：加權失效率 ≥ 觸發閾值（見第四節）

三個條件必須同時滿足才觸發審查。
若條件A或B不滿足，系統輸出：
  「⚠️ 樣本數不足（N={n}），無法進行統計評估，
    維持現行規則，但信心度標記為『低』」
```

### 3.2 樣本數與信心度的對應關係

```
樣本數（同類情境）→ 信心度標記：

N < 5：「極低」（不進行統計評估）
N 5~9：「低」（可進行方向性評估，不可調整閾值）
N 10~19：「中」（可提出調整建議，需Owner確認）
N ≥ 20：「高」（統計結論相對可靠，仍需Owner確認）

注意：即使N≥20，仍需Owner確認才能調整閾值
      系統永遠不自動修改閾值
```

## 四、失效率臨界值與降級邏輯

### 4.1 加權失效率計算

```python
def calc_weighted_failure_rate(cases, current_quarter):
    """
    計算加權失效率
    
    cases: 同類情境的所有案例列表
    current_quarter: 當前季度（用於計算時間衰減）
    """
    import math
    
    total_weight = 0
    failure_weight = 0
    
    for case in cases:
        age = current_quarter - case['quarter']  # 距今季度數
        weight = math.exp(-0.15 * age)
        
        # 結構性轉變前的案例額外衰減
        if case.get('structural_break', False):
            weight *= 0.5
        
        total_weight += weight
        if case['is_failure']:
            failure_weight += weight
    
    if total_weight == 0:
        return None
    
    return failure_weight / total_weight
```

### 4.2 三級臨界值系統

```
GREEN（正常）：加權失效率 < 25%
  → 規則可靠，正常執行
  → 信心度標記：依樣本數決定（見3.2節）
  → 無需特殊處理

YELLOW（警戒）：加權失效率 25%~40%
  → 規則可靠性下降，需要額外謹慎
  → 觸發動作：
    1. 在每次決策輸出中附加警告標籤
    2. 加碼比例自動降低25%（如原計畫50%→37.5%）
    3. 季度稽核時提交Owner審查
  → 不自動修改規則

ORANGE（危險）：加權失效率 40%~60%
  → 規則可靠性嚴重下降
  → 觸發動作：
    1. 強制附加「規則可靠性警告」
    2. 加碼比例自動降低50%（如原計畫50%→25%）
    3. 立即提交Owner緊急審查（不等季度稽核）
    4. 在Owner確認前，訊號自動降一級
       （ADD→HOLD_ADD，HOLD_ADD→HOLD_CAUTION）
  → 不自動修改規則

RED（崩潰）：加權失效率 > 60%
  → 規則可靠性崩潰
  → 觸發動作：
    1. 強制標記：「此規則已暫停，等待Owner重新設計」
    2. 所有依賴此規則的訊號自動降為 actionable: false
       並附加：「規則可靠性不足，請Owner手動判斷」
    3. 立即觸發Owner緊急審核
    4. 在Owner重新確認規則前，使用固定保守預設：
       HOLD_CAUTION（不加碼，不減碼）
  → 不自動修改規則，等待Owner重新設計
```

### 4.3 降級邏輯的認識論說明

```
為什麼不自動修改規則？

原因1：樣本數不足
  即使失效率>60%，可能只有3~4個失效案例
  這不足以支持「規則本身有問題」的結論
  可能只是「市場環境暫時不適合此規則」

原因2：修改規則本身也是一個決策
  修改規則的決策同樣面臨後見之明困境
  自動修改只是把問題轉移，不是解決問題

原因3：Owner的業務判斷不可替代
  規則失效可能有多種原因：
    a. 規則本身有缺陷（需要修改規則）
    b. 市場環境暫時異常（需要等待）
    c. 數據品質問題（需要重新評估案例）
  只有Owner能判斷是哪種原因
```

```
P1（現金守門員）：

P2（SYSTEMIC強制冷靜）：
  支持案例數：1個（2026-06-05 VIX=35）

  支持案例數：3個（2024Q2~Q4）
  加權失效率：~47%（ORANGE）

  已知失效模式：2024Q3/Q4 BLOCK+CAUTION後股價+25.3%
  觸發動作：加碼比例降低50%，提交Owner緊急審查
  認識論警告：🔴 此規則可靠性嚴重下降，
               建議Owner審查是否修改為「BLOCK+CAUTION→BLOCK」

EVA（PB>歷史最高）：
  支持案例數：0個（新規則，無歷史驗證）
  加權失效率：無法計算
  信心度：極低（設計值，未經驗證）
  認識論警告：⚠️ 此規則為新設計，尚無歷史驗證，
               所有基於EVA的決策信心度自動標記為「低」
```

## 六、執行SOP

### 6.1 每次決策時（即時）

```
Step 1：識別使用的規則（P1/P2/P3/EVA）
Step 2：查詢該規則的認識論標籤（本文件第五節）
Step 3：計算當前加權失效率
Step 4：根據失效率等級，調整輸出格式和加碼比例
Step 5：在決策輸出中附加認識論標籤
```

### 6.2 季度稽核時（每季）

```
Step 1：收集過去一季的所有仲裁裁決
Step 2：更新各規則的案例庫（新增案例，更新時間權重）
Step 3：重新計算各規則的加權失效率
Step 4：若有規則進入YELLOW/ORANGE/RED，提交Owner審查
Step 5：更新本文件第五節的「當前各規則認識論標籤」
```

### 6.3 Owner審查時（觸發後）

```
Owner需要回答的問題：
  Q1：失效案例是因為「規則本身有缺陷」還是「市場環境暫時異常」？
  Q2：若是規則缺陷，應如何修改？（修改需記錄在KnownConflicts）
  Q3：若是市場環境異常，預計何時恢復正常？
  Q4：在Owner決策前，系統應使用哪個保守預設？

Owner決策後：
  → 更新規則（若需要）
  → 更新認識論標籤
  → 記錄審查結果至KnownConflicts（ARBITRATION類型）
```

## 七、禁止事項

```
❌ 禁止系統自動修改任何閾值（包括VIX門檻、PB門檻等）
❌ 禁止在樣本數<5時進行統計評估
❌ 禁止將「加權失效率高」直接等同於「規則錯誤」
❌ 禁止忽略認識論標籤直接執行決策
❌ 禁止在RED等級時繼續使用原規則（必須等待Owner確認）
```
